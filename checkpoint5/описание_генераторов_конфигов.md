# Генераторы конфигураций

В проекте используются вспомогательные скрипты для массовой генерации JSON-конфигураций экспериментов. Их задача — автоматически собирать полный набор конфигов по комбинациям датасетов, провайдеров, моделей и наборов настроек в рамках реального контракта конфигурации проекта.
Каждый сгенерированный JSON-файл представляет собой готовую конфигурацию одного эксперимента.

Итогом работы является директория с JSON-файлами, которые затем можно передавать в CLI-команду запуска эксперимента.

## Общий принцип работы

Все такие генераторы построены по одной и той же схеме.

Сначала в коде задаются фиксированные списки:
* датасетов с указанием языков, идентификаторов и путей к SQLite-файлам;
* провайдеров;
* моделей;
* наборов параметров эксперимента;
* общих значений по умолчанию.

После этого генератор проходит по всем предусмотренным комбинациям этих сущностей и для каждой комбинации собирает отдельный JSON-конфиг. Полученная конфигурация затем сохраняется на диск.

## Что входит в каждый сгенерированный конфиг

Независимо от конкретного генератора, итоговый JSON строится из одних и тех же смысловых блоков.

### Идентификатор эксперимента

Для каждого конфига формируется уникальный experiment_id.

### Блок датасета

Генератор формирует секцию dataset, где задаются:
* dataset_id;
* sqlite_path;
* query_mode;
* limit;
* filters.

Этот блок определяет источник данных для эксперимента и параметры выборки строк.

### Блок рантайма

Для каждой конфигурации собирается секция runtime, содержащая:
* имя провайдера;
* имя модели;
* список API-ключей;
* дополнительные сетевые параметры при необходимости;
* таймаут;
* число повторных попыток;
* лимит запросов в минуту;
* температуру;
* ограничение на число выходных токенов.

Этот блок определяет, через какой внешний сервис будет выполняться перевод и с какими ограничениями.

### Блок промпта

Генератор создаёт секцию prompt в полном формате конфигурации проекта. В неё входят:
* profile_name;
* batch_system_prompt;
* batch_user_template;
* single_system_prompt;
* single_user_template;
* batch_mode;
* expects_json_array;
* log_prompts.

Содержимое этого блока определяет, какой профиль построения запросов будет использоваться в пакетном и одиночном режимах.

### Блок защиты

Генератор всегда явно задаёт секцию protection, то есть стратегию обработки и сохранения специальных токенов, плейсхолдеров и других чувствительных фрагментов текста перед отправкой в модель.

### Блок валидации

Во все конфиги добавляется секция validation с именем валидатора и его параметрами. Она определяет правила проверки ответа модели и поведение системы в случаях, когда батч ответ оказался некорректным.

### Общие параметры эксперимента

Помимо обязательных блоков, генератор записывает также общие параметры верхнего уровня:
* batch_size;
* src_lang;
* dst_lang;
* use_cache; (не используется)
* save_raw_responses.

Эти поля управляют режимом выполнения эксперимента и сохранением его результатов.

### Как выбирается размер пакета

Основой служат параметры модели, связанные с допустимой нагрузкой по токенам. Чем меньше токенов в минуту тем меньше размер батча.

Смысл этого механизма — заранее снизить вероятность ошибок формата, переполнения контекста и ухудшения качества при слишком больших пакетах.

### Провайдер-специфические поправки

Хотя общая структура генераторов одинакова, при сборке конфигурации могут добавляться небольшие поправки, зависящие от выбранного провайдера или конкретного варианта исполнения.

### Структура выходных файлов

Сгенерированные конфиги сохраняются в базовую выходную директорию. Внутри неё обычно создаются подкаталоги по идентификатору набора настроек. Каждый файл получает имя, совпадающее с experiment_id.

Типовая структура результата выглядит так:

```
<output_dir>/
  <preset_id_1>/
    <experiment_id_1>.json
    <experiment_id_2>.json
  <preset_id_2>/
    <experiment_id_3>.json
    ...
```

## Интерфейс запуска генераторов

Все генераторы используют одинаковый интерфейс командной строки:
* `--out-dir` — базовая директория для записи JSON-конфигов;
* `--providers` — список провайдеров, для которых нужно строить конфиги.

Если список провайдеров не указан явно, генерация обычно выполняется для всех поддерживаемых вариантов, заданных в скрипте.
