Translator Benchmark — обзор экспериментов

1. Назначение проекта

Проект представляет собой систему бенчмаркинга для экспериментов с машинным переводом на базе языковых моделей.

Основная идея — вся логика эксперимента полностью задаётся через JSON-конфигурацию.

Основной pipeline

config -> translation -> storage -> evaluation -> reporting

Система позволяет:
* запускать массовые эксперименты перевода;
* сохранять детальные результаты и попытки вызовов моделей;
* вычислять несколько типов метрик (качество, классические, API);
* формировать сводные отчёты и сравнения экспериментов.

--- 

2. Что было реализовано

2.1 Конфигурационная модель экспериментов

Эксперимент полностью описывается JSON-конфигом.

Ключевые блоки:
* dataset — источник данных (SQLite);
* runtime — провайдер и модель;
* prompt — шаблоны запросов;
* protection — защита служебных токенов;
* validation — проверка ответа модели.

Что это даёт:
* воспроизводимость экспериментов;
* управляемость через параметры;
* масштабирование запусков без изменения кода.

--- 

2.2 Генерация конфигураций

Реализованы генераторы конфигов, которые:
* перебирают комбинации датасетов, моделей, провайдеров и настроек;
* создают отдельный JSON-конфиг для каждого эксперимента;
* сохраняют их в структуру каталогов;
* позволяют запускать эксперименты пакетно.

Подробнее: [описание_генераторов_конфигов.md](./описание_генераторов_конфигов.md)￼

--- 

2.3 Пайплайн перевода

Полный процесс выполнения:
	1.	Загрузка данных из SQLite
	2.	Защита токенов
	3.	Разбиение на батчи
	4.	Вызов модели
	5.	Валидация ответа
	6.	Fallback на одиночный режим
	7.	Восстановление токенов
	8.	Сохранение результатов

Особенности:
* batch-first (эффективность);
* fallback на single (устойчивость);
* строгая валидация ответа.

Подробнее: [описание_кода.md](./описание_кода.md)￼

--- 

2.4 Runtime слой (работа с LLM)

Реализована инфраструктура взаимодействия с моделями:
* поддержка провайдеров (groq, deepseek);
* ротация API-ключей;
* retry и fallback логика;
* обработка rate limit;
* контроль таймаутов.

--- 

2.5 Промпты и экспериментальные пресеты

Реализована система профилей промптов.

Основные группы экспериментов
* Базовые: strict_json, natural, literal
* Контроль токенов: placeholder_strict
* Few-shot: 1 пример / несколько / edge cases
* Raw токены: без защиты

Проверяемые гипотезы
* влияние строгости формата;
* влияние естественности формулировки;
* влияние буквальности;
* влияние защиты токенов;
* влияние few-shot и структуры примеров.

Подробнее: [описание_экспериментов.md](описание_экспериментов)￼

--- 

2.6 Валидация и отказоустойчивость

Реализована система проверки ответов модели:
* проверка JSON;
* проверка длины батча;
* попытка восстановления;
* fallback на одиночные вызовы.

--- 

2.7 Хранение результатов

Используется SQLite.

Основные таблицы:
* experiments — параметры эксперимента;
* results — переводы;
* attempts — все вызовы модели;
* metrics — агрегированные метрики;
* api_metrics — поведение API;
* classic_metrics — BLEU, chrF, TER, COMET.

Позволяет анализировать:
* качество;
* стабильность;
* стоимость (через токены);
* поведение модели.

--- 

2.8 Оценка и отчёты

Реализованы уровни оценки:
	1.	Quality-метрики (через legacy адаптер)
	2.	Классические метрики (BLEU, chrF, TER, COMET)
	3.	API-метрики (ошибки, ретраи, токены)
	4.	Token efficiency

Команды:

translator-benchmark evaluate-experiment --experiment-id <id>
translator-benchmark experiment-summary --experiment-id <id>
translator-benchmark leaderboard

Подробнее: [описание_запуска_и_конфигов.md](./описание_запуска_и_конфигов.md)￼

3. Ход экспериментов

Эксперименты строятся как комбинации:
* модель / провайдер;
* профиль промпта;
* стратегия защиты;
* batch_size;
* few-shot;
* стиль инструкции.

Это формирует матрицу экспериментов, где изолированно проверяются гипотезы.

Основные направления
* формат vs естественность;
* literal vs paraphrase;
* zero-shot vs few-shot;
* влияние структуры примеров;
* влияние защиты токенов;
* устойчивость батчевого режима.

Все эксперименты:
* генерируются автоматически;
* запускаются через CLI;
* сохраняются в единую БД;
* сравниваются через leaderboard.

Правда эксперимент с fewshot пошел не по плану из-за очепятки в конфиге. В итоге там скорее проверяется как моделька справляется с примерами из несуществующих штук.
Т.к. по конфигам произошла защита тегов на заглушки, которых нет в примерах.
С rawtoken все ок.

Эксперименты запускались на двух языковых парах:
* en -> ru
* zh -> ru

--- 

5. Ключевая идея

Система построена так, чтобы:
* не менять код при изменении эксперимента;
* масштабировать эксперименты через генерацию конфигов;
* разделить выполнение, хранение и оценку;
* сравнивать эксперименты на единой базе.
