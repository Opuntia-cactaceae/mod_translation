Основная идея этого бенчмарка — вся логика эксперимента задаётся через JSON-конфиг.

Основной путь:

config -> translation -> storage -> evaluation -> reporting

---

CLI

Запуск эксперимента

python -m translator_benchmark.cli.main run-experiment <config.json>

---

Оценка

python -m translator_benchmark.cli.main evaluate-experiment --experiment-id <id>

или

python -m translator_benchmark.cli.main evaluate-experiment --config <config.json>

---

Дополнительные команды

api-summary           вычисляет метрики API (успешность, ретраи, токены, ошибки)
experiment-summary    собирает полный отчёт по эксперименту (качество + API + агрегаты)
classic-summary       собирает классические метрики машинного перевода (BLEU, chrF, TER, COMET)
leaderboard           показывает сравнение экспериментов по ключевым метрикам
list-registry         выводит доступные runtime / prompt / protection / validation (штуки для конфигов)

---

Общая структура конфига

{
  "experiment_id": "string",
  "dataset": { ... },
  "runtime": { ... },
  "prompt": { ... },
  "protection": { ... },
  "validation": { ... },
  "batch_size": 10,
  "src_lang": "en",
  "dst_lang": "ru",
  "use_cache": true,
  "save_raw_responses": false
}

Обязательные поля конфигурации


experiment_id — уникальный идентификатор эксперимента. Используется как ключ для хранения всех результатов, метрик и логов. Позволяет сравнивать запуски и не терять историю.

dataset — источник данных. Определяет, какие строки попадут в эксперимент. Влияет на выборку, качество оценки и репрезентативность результатов.

runtime — LLM-провайдер и модель. Определяет фактическое поведение модели: качество перевода, скорость, стоимость и стабильность (retry/fallback).

prompt — шаблоны взаимодействия с моделью. Определяет инструкцию и формат ответа, напрямую влияет на стиль и корректность перевода.

protection — стратегия защиты токенов. Определяет, какие части текста нельзя трогать модели и как они будут восстановлены.

validation — правила проверки ответа модели. Определяет, что считается корректным ответом и когда включается fallback.

Опциональные (с дефолтами)
* batch_size = 10
* src_lang = “en”
* dst_lang = “ru”
* use_cache = true
* save_raw_responses = false

Dataset

{
  "dataset_id": "sqlite",
  "sqlite_path": "path/to/db.sqlite",
  "query_mode": "full",
  "limit": 100,
  "filters": {}
}

Поля

dataset_id — тип загрузчика (сейчас используется sqlite)

sqlite_path — путь к базе данных

query_mode — режим загрузки (обычно full)

limit — ограничение количества строк

filters — фильтрация по полям

Фактическая структура данных

Эксперимент работает со строками таблицы (translations), где используются:

row_id — идентификатор строки

source_text — текст для перевода

reference_text — эталон (если есть)

src_lang, dst_lang — языки

дополнительные метаданные (опционально)

Важно:

обязательным фактически является только source_text
reference_text нужен для метрик

Prompt

  "profile_name": "json_batch",
  "batch_system_prompt": "...",
  "batch_user_template": "...",
  "single_system_prompt": "...",
  "single_user_template": "...",
  "log_prompts": false
}

Профили промптов

Поддерживаемые профили:
* simple_single
* json_batch

Различия

simple_single

только одиночные запросы

без обработки батчами

без запасного способа на случай ошибки

максимально надёжный, но медленный и затратный по токенам (гипотеза)

json_batch

батчевые запросы

ожидает JSON-массив

есть падение на single профиль в случае ошибки


---

Protection

{
  "strategy_name": "xml_placeholders",
  "options": {}
}

Доступные стратегии:
* none
* legacy_game_tokens
* xml_placeholders

legacy_game_tokens и xml_placeholders используют один и тот же набор шаблонов для обнаружения токенов ($VAR$, [Root.GetName], £food£, §Y…§!, {VALUE}, %sd, \n), но различаются форматом XML‑плейсхолдера и именем атрибута id.
legacy_game_tokens = <PH id="k{N}"/>  
xml_placeholders = <protected id="xml{N}"/>

Validation

  "validator_name": "composite",
  "options": {
    "allow_fallback_on_json_error": true
  }
}

Полный путь получения отчёта по эксперименту

Типичный сценарий от запуска перевода до сравнения результатов:

1. Запустить эксперимент перевода (сохраняет результаты в БД):
   python -m translator_benchmark.cli.main run-experiment <config.json>

2. Вычислить агрегированные quality-метрики (сохраняет в БД):
   python -m translator_benchmark.cli.main evaluate-experiment --experiment-id <id>

3. Вычислить API-метрики (сохраняет в БД):
   python -m translator_benchmark.cli.main api-summary --experiment-id <id>

4. Вычислить классические метрики машинного перевода (сохраняет в БД):
   python -m translator_benchmark.cli.main evaluate-classic --experiment-id <id>
   (--with-comet для подсчёта COMET)

5. Показать сводный отчёт по эксперименту (только вывод):
   python -m translator_benchmark.cli.main experiment-summary --experiment-id <id>

6. Показать отдельный отчёт по классическим метрикам (только вывод):
   python -m translator_benchmark.cli.main classic-summary --experiment-id <id>

7. Сравнить эксперименты между собой (только вывод):
   python -m translator_benchmark.cli.main leaderboard

Дополнительная команда для просмотра доступных компонентов:
   python -m translator_benchmark.cli.main list-registry

Что сохраняется в БД:
- run-experiment: результаты перевода и попытки вызовов
- evaluate-experiment: quality-метрики (текст, теги, компилируемость, успешность)
- api-summary: метрики API (успешность, ретраи, токены, ошибки)
- evaluate-classic: классические метрики (BLEU, chrF, TER, COMET)

Что только выводит отчёт:
- experiment-summary: объединяет все сохранённые метрики
- classic-summary: показывает классические метрики
- leaderboard: сравнивает эксперименты
